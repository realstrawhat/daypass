N = min(floor(sqrt(239.504 kB) + 1), 10) = min(floor(15.48 + 1), 10) = min(16, 10) = 10.

- **Reused idempotency key can book the wrong slot (`components/BookingPanel.tsx`, `createHold` in `lib/bookings.ts`).** `key` is created once per panel and only rotates inside `pay()`, after a decline. `createHold` returns any prior row with that key and never compares gym or time.
  - Pick 10:00, open the wallet, close it, pick 11:00, book again. The server returns the 10:00 hold, the wallet shows 11:00, and paying confirms 10:00.
  - The same lookup returns `failed` and `expired` rows. Closing the wallet after a decline, or letting a hold run out, leaves checkout failing with `hold_ended` until the page reloads, because `holdId` is only cleared on `declined`.
  - The fix is a new key per slot selection, plus a server check that the key matches the gym and slot and that the row is still a live hold.

- **`changeBooking` charges before it knows the move will succeed (`lib/bookings.ts`).** `charge()` runs before the atomic SQL. If that statement then fails with `slot_full`, `stale`, `too_late` or a unique violation, the customer has paid the difference. There is no refund, payment row or compensation path. Concurrent PATCHes can each charge, while only one wins.

- **Price can change without the buyer seeing it (`changeBooking`, `ChangeFlow`, `BookingPanel`).** The client compares against `b.price_cents` or the price rendered with the page, and the server uses the gym's current price. No expected amount is sent.
  - If a partner raises the price after booking, the UI shows no difference and `confirm()` sends no method. The server then charges the gap to the default `demo-card`.
  - The wallet total at first checkout can also differ from the held `price_cents`.
  - The server should require an expected amount, and require an explicit method whenever `difference > 0`.

- **The payment boundary is not what its comment says (`lib/payments.ts`).** The comment says a real provider "would replace `charge` and nothing else", but:
  - `charge` takes no idempotency key, so concurrent `payHold` calls would each charge.
  - Nothing returns a provider reference, and there is no `payments` column to store one.
  - No refund function exists. `cancelBooking` and the refund branch of `changeBooking` just insert `refund/succeeded` rows.
  - `cancelBooking` hardcodes `method = 'demo-card'`, even for wallet payments.

- **Holds have no visible expiry and stale holds block availability (`lib/gyms.ts`, `lib/bookings.ts`, `WalletSheet`).**
  - `getAvailability` never calls `releaseExpiredHolds`, and there is no cron in `vercel.json`. An expired hold keeps a slot full until someone runs checkout somewhere.
  - `hold_expires_at` is returned but the UI ignores it, so there is no countdown.
  - Closing the wallet does not release the hold.
  - The expiry error is shown with "Choose another card to try again", which cannot work.
  - `bookings` has no partial index on `(hold_expires_at) WHERE status = 'hold'`, yet this update runs on every checkout.

- **Account deletion is only a flag (`app/api/account/route.ts`, `lib/auth.ts`, `scripts/setup-db.mjs`).** The UI and privacy notice promise erasure within 30 days, but nothing in the diff does it.
  - Neither `getCurrentUser` nor the password and passkey login paths check `deletion_requested_at`, so the user can log straight back in with no sign the request is pending and no way to withdraw it.
  - Upcoming bookings are not cancelled, refunded or released.
  - A future hard delete cascades through `bookings` and `payments`, which removes financial records and reduces other partners' "Commission owed".
  - `owner_user_id ON DELETE SET NULL` would leave a deleted partner's gyms live with no owner.

- **No account recovery or credential management (`app/api/auth/[action]/route.ts`, `AccountClient`).** There is no forgotten-password flow, email verification, password change or email change. Passkeys cannot be listed or removed, so a lost device stays trusted. There is no "log out everywhere". A mistyped signup email or a forgotten password locks the user out, and the 409 then stops them re-registering.

- **No transactional messages.** Nothing sends a booking confirmation, a change or cancel notice, or a reminder. The "day-before reminder" exists only if the user imports the `.ics` file. Calendar events do not update after a cancel, because the route returns 404 instead of a `CANCEL` or tombstone event.

- **Nothing verifies a pass at the gym.** The QR encodes `DAYPASS:<code>` and the pass says "Show at the desk", but there is no lookup or check-in endpoint, no redeemed state and no partner arrivals list. Staff cannot confirm that a code is real, for today, not cancelled or not already used. Cancelled passes still render their QR, only visually voided. Partner "Visits" counts confirmed bookings, including future ones, rather than actual visits.

- **Pass needs a live connection at the door.** `app/manifest.ts` declares `display: standalone`, but no service worker or cached pass exists, and the wallet is preview-only. A gym basement with poor signal means the code cannot be shown. Caching the pass, or at least the code, on the device would close this.

- **New partner gyms display a fake 0.0 rating and sink in ranking (`app/api/partners/route.ts`, `lib/gyms.ts`).** Partner inserts leave `seed_rating_count = 0`, so the rating formula yields NULL.
  - `Number(null).toFixed(1)` renders "0.0" on gym pages, search cards and home picks.
  - The whole `recommended` expression becomes NULL, so `NULLS LAST` puts these gyms at the bottom regardless of distance or price.
  - A "New" state and a neutral ranking fallback are missing.

- **Partner listing has gaps (`app/api/partners/route.ts`, `PartnerClient`).**
  - It goes live instantly with `is_demo = false` and no verification.
  - `lat` and `lng` have no range check and no check against the city. `null` or whitespace coerces to 0, which counts as a valid pin at 0,0.
  - The form has no opening hours, so defaults are published under "Details confirmed by the gym".
  - It has no photos, and no way to edit details, block times, pause or delist after creation.
  - "Confirm details" is tied to saving a price.
  - The 90-day rule is not enforced, so overdue gyms stay listed and bookable.
  - "Commission owed" has no invoicing or settlement path.

- **Review integrity and reviewer privacy (`addReview`, `addSamplePastVisit`, `getReviews`).**
  - `addReview` does not exclude `is_sample`, so every new account can post a real public review of `iron-gym-amsterdam` without visiting, and it counts toward the rating.
  - Owners can book and rate their own gym.
  - `getReviews` publishes the user's full `users.name`, while seed reviews use "Mara K." The privacy notice never says reviews are public.
  - There is no report, moderation or delete path.

- **Public GET requests write unbounded demo data (`app/api/gyms/route.ts`, `ensureCityHasGyms`, `seedCity`).**
  - An unauthenticated `?city=` triggers about 96 sequential database round trips and permanently adds rows, with no rate limit.
  - A timeout partway leaves `n > 0`, so that city never finishes seeding.
  - Same-name cities such as Paris, Texas collide on slug (always `iron-gym-paris`, and any other repeated name), and those gyms are silently skipped.
  - `geocodeCity` has no timeout. A geocoder outage returns "No place called X… check the spelling", or a 500 if the fetch throws.
  - Taking only `count=1` gives users no way to choose between ambiguous places. A partner's gym can get the wrong country or timezone this way.

- **Open redirect in `safeNext` (`app/login/page.tsx`).** `/\evil.com` passes the `startsWith('/')` and not `startsWith('//')` checks. Browsers treat `\` as `/`, so `window.location.assign(next)` in `LoginClient` and the server `redirect()` for logged-in users can both land on an external site after login. It should parse the value with `new URL(next, origin)` and require the same origin.

- **No abuse controls on sensitive endpoints.** Login, register, passkey and checkout have no rate limit or lockout. One account can hold every slot at a gym, repeatedly and for free, because active holds are not capped. Login also returns faster for unknown emails, since scrypt only runs when a row exists.

- **Security headers are incomplete (`next.config.mjs`).** There is no `Content-Security-Policy`, `frame-ancestors` or `X-Frame-Options`, so account deletion, cancellation and checkout screens can be framed. No CSP backs up the `dangerouslySetInnerHTML` in `HoloPass`, and this config has no allowlist for the map tile hosts.

- **The location and privacy claims are not supported (`app/api/gyms/route.ts`, `GymSearch`, `app/privacy/page.tsx`).**
  - Coordinates go in the GET query string (`/api/gyms?lat=&lng=`), so platform request logs can capture them despite the comment "not stored or logged".
  - The notice omits OpenFreeMap, which receives tile requests around the user's position, and Open-Meteo, which receives typed cities and home city.
  - It also omits public review names, a contact, retention periods and legal basis.
  - Signup has no acknowledgement of the notice, and there is no terms or refund page.

- **24-hour rule is not disclosed before purchase (`BookingPanel`, `WalletSheet`).** The panel always says "Free to change or cancel until 24 hours before", including for slots under 24 hours away, which are never changeable. Buyers only learn this after paying. Also missing are the no-show policy, what happens if a gym closes or cancels, and what to bring. Times are never labelled as gym-local, which matters when booking another city from a different timezone.

- **A session becomes "Past visit" the moment it starts (`app/bookings/[id]/page.tsx`, `addReview`).** `isPast` is `start <= now`, although the calendar models a one-hour session. At 10:01 someone at the desk sees "Past visit", loses the manage actions, and is asked to rate a visit that has barely begun. This should use the session end.

- **Client flows stick on network failure.** `CancelFlow.confirm`, `RateVisit.submit`, `PartnerClient.submit` and `removeAccount` do not catch fetch or `res.json()` errors. Their busy states then stay on "Cancelling" or "Saving", or the action fails silently. `ChangeFlow.openGyms` stays on "Loading gyms" forever if the fetch rejects. `savePrefs` and `removeCard` also lack a catch, and `removeCard` gives no failure message. `HeroSearch` writes to `sessionStorage` unguarded, so a storage error leaves "Locating" stuck.

- **Server input errors surface as 500s (`app/api/*`, `lib/gyms.ts`).** Most routes call `req.json()` with no catch, so malformed JSON gives 500 rather than 400. `app/api/partners` PATCH casts an unvalidated `id` to `::uuid`. Passkey verification lets library exceptions fall through as "Something went wrong". `home_city` and `max_price_cents` accept negative or unbounded values. `bbox` has no size limit, so one request can compute correlated ratings across the whole `gyms` table.

- **Search state is not restorable (`components/GymSearch.tsx`).**
  - Sort, filters, page, bbox and view live only in component state. Browser back from a gym page drops them, and a results URL cannot be shared.
  - `/gyms?near=me` deletes its stored location on first read, so back triggers another geolocation request.
  - Pressing "Near me" from a `?city=` page leaves the old city in the URL.
  - A saved max price such as €12 has no matching `PRICES` option, so the filter is active while the select does not reflect it.

- **`role="radio"` controls lack radio keyboard behaviour (`SlotPicker`, `RateVisit`, `WalletSheet`).** Each radio is a separate tab stop with no arrow-key handling or roving `tabindex`, which breaks the pattern screen-reader users expect. The rating stars also expose only an exact `aria-checked`, while the visual fill suggests a range. The skip link targets a non-focusable `<div id="main">`.

- **Tests miss the highest-risk paths and can pass without checking (`tests/booking-rules.test.mjs`).**
  - The 24-hour test silently `return`s when no near slot exists or the hold fails, so it passes without asserting anything.
  - "Paying twice charges once" only checks spot count, and never counts charges or `payments` rows.
  - "Only the owner can see a booking" only tries a stranger's DELETE, not pay, PATCH, calendar or the page.
  - Nothing covers hold expiry, key reuse with a different slot, reviews, partners, passkeys, account deletion, or timezone and DST slot logic.
  - The suite needs a running server, live Open-Meteo and whatever database is configured. It leaves QA users and bookings behind.
  - `tests` and `scripts` are excluded from `tsc`, and there is no lint script or CI config.

- **Project setup and schema evolution are missing (`package.json`, `scripts/setup-db.mjs`).**
  - The project has no README or `.env.example`, so `DATABASE_URL`, `db:setup` and the test prerequisites are undocumented.
  - `next`, `react`, `react-dom`, the Neon driver and `typescript` are declared as `"latest"`, so any reinstall that regenerates the lockfile can cross a major version.
  - `CREATE TABLE IF NOT EXISTS` is the only migration mechanism, so later column or constraint changes are silently skipped on existing databases.
  - Nothing purges expired `sessions`.

## Other findings

- **Wrong slot paid for.** `components/BookingPanel.tsx:30` keeps one idempotency key while the panel is open, and `createHold` returns any earlier booking with that key without comparing gym or time (`lib/bookings.ts:61-62`). If someone holds slot A, closes the wallet, picks slot B and books, the sheet shows B but the payment confirms A.
- **Checkout stuck until reload.** With the same reused key, closing the wallet after a decline or an expired hold returns the old `failed` or `expired` row, and paying gives 409 `hold_ended`. The message says to pick a slot again, but that cannot help until the page is reloaded. The retry in `BookingPanel.tsx:72-73` only runs while the wallet stays open after a decline.
- **Silent charge or refund on a same-gym time change.** `ChangeFlow` starts with the booked price (`components/BookingActions.tsx:132`), so it shows no difference. The server uses the gym's current price (`lib/bookings.ts:161-164`). If a partner changed the price after booking, the user is charged on `demo-card` by default, or refunded, without seeing it.
- **Charge taken before the spot is secured.** `changeBooking` charges at `lib/bookings.ts:164`, before the atomic move. A `slot_full`, `stale` or `already_booked` result leaves that charge with no ledger row and no reversal.
- **Concurrent pays both call `charge`.** `payHold` calls `charge` at line 113 before its guarded update, and no idempotency key is passed. This is harmless while simulated, but `lib/payments.ts` says a real provider would replace `charge` and nothing else.
- **Open redirect after login.** `safeNext` (`app/login/page.tsx:8`) accepts `/\evil.example/x`. I checked this with Node: `new URL` resolves it to `https://evil.example/x`, and `LoginClient.tsx:6` passes it to `window.location.assign`.
- **Deletion request has no follow-through.** Only `app/api/account/route.ts:22` writes `deletion_requested_at`, and nothing acts on it. Login still works afterwards, and no job erases the account, though the UI and privacy page promise erasure within 30 days. `process-log.md:52` already notes that erasure is not automated.
- **Expired holds keep showing as taken.** `getAvailability` (`lib/gyms.ts:174`) never releases expired holds. A slot stays unavailable until someone's checkout triggers `releaseExpiredHolds`.
- **Price filter shows the wrong value.** A saved limit such as €12 is accepted, but the filter options are only any, €10, €15 and €20 (`GymSearch.tsx:188`). The select then falls back to showing "Any price" while the €12 limit still applies.
- **New partner gyms show a 0.0 rating.** They have a zero seed count, so `rating` is NULL, and `Number(null).toFixed(1)` displays "0.0" (`app/gyms/[slug]/page.tsx:54,84`).
- **Tests leave data behind.** The test file has no cleanup, and `process-log.md:43` records running it against the real database. Each run leaves QA accounts and confirmed bookings that use up real slots.

# Daypass: implementation process log

This records what happened during the build, including failures and how each was corrected and checked.

Scope note: the workshop asks for one story from the Unit 7 pack. The project owner asked for everything in the build pack, so the full scope was built. Story 3, "Book an appointment", is a good one to present as the main story.

## BMad workflow used

| Stage | What was used | Output |
|-------|---------------|--------|
| Setup | BMad v6.12.4 installed in the project, plus AGENTS.md and .gitignore from the course boilerplate | `_bmad/`, `.agents/` |
| Plan | `bmad-build-auto` steps 1 and 2 | `spec-daypass-full-scope.md` |
| Implement | `bmad-build-auto` step 3, with one deviation below | App source |
| Check | `bmad-build-auto` step 4: Blind Hunter, Edge Case Hunter, Verification Gap and Intent Alignment reviewers | Review Triage Log in the spec |

### Deviations from the BMad workflow

- Step 3 says a fresh subagent implements from the spec. The code was written directly in the main session, so that the owner's live feedback could be applied as it arrived.
- Steps 1 to 3 were read and followed out of the strict order. Implementation began before steps 3 and 4 had been read, and step 4 ran later.
- There is no Git repository, so the review ran against a generated diff of all source files instead of a real diff, and no baseline revision exists.
- BMad's separate PRD, architecture and epics workflows were not run. The Unit 7 build pack already held that planning, so the spec points to it directly.

## Limits to state honestly

- Gyms, prices and reviews are invented sample data, so NFR8 (pin within 50 m of the real entrance) cannot be shown.
- Payment is simulated at the owner's request. No external provider is connected, so FR6 is met in the flow but not its "external payment provider" part.
- The wallet pass is a preview. A real one needs Apple and Google developer accounts.
- The day-before reminder is an in-app banner and a calendar alert. No email or push is sent.
- Account deletion erases the account at once (row 60). Until 6 November it only recorded the request, which this list said.
- NFR5 is met: passwords are hashed with scrypt, all traffic is HTTPS, and a login ends after 30 days unused, because the cookie renews each time the app opens. An earlier version of this list wrongly said it was only partly met (row 58).
- Face ID uses passkeys. The setup step was reached, but a real Face ID login was not completed on a physical device.
- NFR3 needs five real test users. NFR9 was not measured under load. NFR10 can only be measured over time.
- NFR1 is partly met in a phone simulation (row 59): the gym list and its pins show in about 1.4 s, but the full street map takes about 6 to 7 s. Not measured on a real mid-range phone.
- NFR2 was tested in Chrome on every main screen at 360 px, and only partly in the Safari engine. Firefox was not tested.
- NFR8's 90-day re-confirmation shows its date and can be renewed, but nothing happens if a gym misses it.
- WCAG 2.2 AA was designed for but not formally audited. Removing the Home pause button goes against WCAG 2.2.2, at the owner's request (row 66).
- The front desk panel shows real people's first name and last initial, pass code, gym and times to anyone with the admin password (row 71). That password is short and shared with the class, and attempts aren't limited, so it is weak protection for real names. A real launch would need proper staff accounts, each tied to their own gym.
- A check-in from a demo login is a real scan of a real record, so it appears on the panel, as "Sam D.". The gyms themselves are still sample data.
- Haptics have not been felt on any real phone by Claude. The iPhone route depends on community reports of how iOS 26.5 behaves, so it could stop working in a later iOS. A swipe can't tick on the newest iPhones, because only a tap counts, and nor can a moment with no finger on the glass, such as a payment finishing.
